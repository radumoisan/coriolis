    Configuration for a simple app¶

    Project template¶

    Info

    I'm using a simple python app for test in this exercise. You can clone the source code from git@github.com:virtomat/ci-test-repo.git

    Regardless of the language (python, java, Angular, etc) the project structure is the same. It looks like this:

    radu@ThinkPad-L380$ tree -L 2
.
├── docs
│    ├── build_and_deploy.md
│    └── configuration.md
├── helm
│    ├── Chart.yaml
│    ├── templates
│    │    ├── deployment.yaml
│    │    ├── ingress.yaml
│    │    └── service.yaml
│    └── values.yaml
├── app.py
├── logger.py
├── Dockerfile
├── requirements.txt
└── README.md
    • docs - This is a directory dedicated for documentation related to this app. It is usually automatically build to a static html site with mkdocs.
    • helm - This is the Helm Chart definition. Notice the templates directory. A basic setup will require a deployment (the actual container in a pod), a service (expose the pod on the internal network) and an ingress (basic layer 7 routing rules, to expose the app outside the cluster)
    • app.py - Test app code (Flask app)
    • logger.py- Some logging setup I find useful.
    • Dockerfile - Dockerfile to build the container
    • README.md - Optional Readme file (deprecated in favor of docs directory).

    Pipeline templates¶

    A pipeline template is pretty basic at this point (expected to be extended in functionality), and only specifies the steps in the pipeline. The definition is supported as json content and we use REST API to push and pull the template definitions.

    For the Default template the json looks like this: 

    {
  "Default": {
    "pvc": {
      "required": true,
      "size": "1Gi"
    },
    "steps": [
      {
        "icon": "feather:github",
        "name": "git-clone"
      },
      {
        "icon": "docker_decolorize",
        "name": "kaniko-build"
      },
      {
        "icon": "helm",
        "name": "helm-update"
      },
      {
        "icon": "heroicons_mini:arrow-path-rounded-square",
        "name": "cleanup"
      }
    ]
  }
}

    • pvc - This is the spec for a volume where the workspace will be. All steps in the pipeline will share this workspace.
    • steps - This are the steps in the pipeline. The execution will follow the order specified here. The naming is also important, as each step name becomed the prefix in finding the right manifest for the job.
    Create/Update a template definition: (expand to see) 
    curl --location 'http://ci.virtomat.dev/conductor/templates' \
--header 'Content-Type: application/json' \
--data '{
    "Default": {
        "pvc": {
            "required": true,
            "size": "1Gi"
        },
        "steps": [
            {
                "name": "git-clone",
                "icon": "feather:github"
            },
            {
                "name": "kaniko-build",
                "icon": "docker_decolorize"
            },
            {
                "name": "helm-update",
                "icon": "helm"
            },
            {
                "name": "cleanup",
                "icon": "heroicons_mini:arrow-path-rounded-square"
            }
        ]
    }
}'

    Note

    You can have as many templates as you want. Each template defines a new kind of pipeline.

    Pipeline configs¶

    For the test app the json looks like this: 

    {
  "templateName": "Default",
  "steps": {
    "git-clone": {
      "git_repo_url": "gitlab.com/virtomat/ci-test-repo.git",
      "git_branch": "main",
      "logging": "DEBUG",
      "webhook_secret": "4F2XqXXk",
      "ttlSecondsAfterFinished": 120
    },
    "kaniko-build": {
      "logging": "DEBUG",
      "ttlSecondsAfterFinished": 120
    },
    "helm-update": {
      "logging": "DEBUG",
      "ttlSecondsAfterFinished": 120
    },
    "cleanup": {
      "logging": "DEBUG",
      "docs_repo_url": "https://github.com/virtomat/voyager-docs.git",
      "ttlSecondsAfterFinished": 120
    }
  }
}

    • templateName - references the template name (it has to exist)
    • steps - The steps in the pipeline must follow the naming in the template.
      • git-clone - This step will clone the git repo in the workspace directory.
      • kaniko-build - This is the build steps (builds the container and pushes it to the registry)
      • helm-update - This is the helm update step (version increment) and published the Chart to registry
      • cleanup - Some cleanup tasks.

    Simulating github trigger¶

    You can use a curl call to trigger a pipeline (just replace the repo url with your own repo url):

    GitHub trigger (expand to see) 
    curl --location 'https://ci.virtomat.dev/conductor/githubTrigger' \
--header 'Content-Type: application/json' \
--data '{
    "ref": "refs/heads/main",  
    "repository": {
        "clone_url": "https://github.com/virtomat/ci-test-repo.git"  
    }
}'
    GitLab trigger (expand to see) 
    curl --location 'https://ci.virtomat.dev/conductor/gitlabTrigger' \
--header 'Content-Type: application/json' \
--data '{
    "ref": "refs/heads/main",
    "repository": {
        "git_http_url": "https://gitlab.com/virtomat/ci-test-repo.git"
    }
}'
